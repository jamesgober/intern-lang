# intern-lang v1.1.0: Keyed hash

**Minor.** v1.1.0 keys the dedup index's hash per interner, so strings built
ahead of time to collide can no longer make interning quadratic. Two seeded
constructors are added. Nothing is removed or changed in the existing API, and
every 1.0 guarantee still holds.

## What is intern-lang?

A string interner. It maps each distinct string to a small, copyable `Symbol`,
stores the bytes once in a contiguous backing store, and hands back integer
handles. Comparing two names then becomes an integer comparison rather than a
byte walk.

## Security: hash flooding

The dedup index is open addressing with linear probing. A lookup starts at the
string's home slot and walks forward until it finds the string or an empty slot,
so strings that share a home slot make each other slower.

Through 1.0.1 the hash had no key. The 1.0.1 finalizer stopped ordinary
identifiers from clustering, but anyone could still study the function and
compute, once and offline, a large set of strings that all land in one slot with
one cached fingerprint. Every `intern` or `get` of those strings then walked the
whole set and compared bytes at each step. 16,000 such 16-byte identifiers took
0.72 s to intern against 0.0013 s for ordinary names, and the cost grows with
the square of the count. In a `ConcurrentInterner` the write lock was held for
the whole walk, so readers stalled too. A front end that interns identifiers or
string literals from untrusted source was exposed.

### The fix

The index now hashes with **SipHash-1-3**, the keyed hash behind the standard
library's default `HashMap` hasher, under a 128-bit key held by each interner.

- With the `std` feature (the default), `Interner::new`, `with_capacity` and
  `Default`, and the `ConcurrentInterner` equivalents, draw the key from
  `std::hash::RandomState`. Each interner gets its own key, so a set of strings
  found to collide in one interner says nothing about the next.
- Without `std` there is no source of randomness in `core`, so the default key
  is a fixed constant. A `no_std` caller facing untrusted input passes a secret
  random seed to the new `with_seed` constructor.

Why SipHash rather than a key mixed into the old multiply-rotate hash: that
round function is simple enough that some input differences cancel out whatever
the key is, so large collision sets could still be built without knowing it.
SipHash is designed as a keyed pseudo-random function, so
without the key, finding collisions is no easier than guessing. The SipHash
code is about forty lines in the crate, with no new dependency, and a test
checks it bit for bit against the standard library's SipHash-2-4 at every length
up to 200 bytes.

Symbol ids do not depend on the key. They are assigned in interning order by
every constructor, so the same sequence of strings yields the same symbols in
every interner, seeded or not. A test pins this.

### Measured

The same 16,000 precomputed identifiers now intern in about 0.002 s. A new unit
test builds 4,000 strings the way an attacker would for the old hash and checks
probe counts under the default constructor: on 1.0.1 they average 2,000.5
probes per key, on 1.1.0 they stay under the bound of 3 that every other corpus
meets.

## Added

```rust
impl Interner {
    pub fn with_seed(seed: u64) -> Self;
    pub fn with_capacity_and_seed(capacity: usize, seed: u64) -> Self;
}

impl ConcurrentInterner {
    pub fn with_seed(seed: u64) -> Self;
    pub fn with_capacity_and_seed(capacity: usize, seed: u64) -> Self;
}
```

The same seed always gives the same index layout, which makes probe counts and
timings reproducible. That is also the risk: anyone who knows the seed can
compute colliding strings. Do not use a fixed or guessable seed for input you
do not control. Use `new` under `std`, or a seed from a secure random source.

## Performance

The keyed hash costs more than the old one. Measured on the development machine
(Windows x86_64, Rust 1.100) with 1.0.1 and 1.1.0 linked into one binary and run
in alternation, median of nine rounds, repeated three times, on pseudo-random
identifiers of 1 to 12 bytes:

| Operation | 1.0.1 | 1.1.0 |
|---|---|---|
| `intern`, repeat hit | 14.3 to 15.6 ns | 20.5 to 24.6 ns |
| `get`, miss | 5.4 to 6.5 ns | 11.0 to 15.6 ns |
| `resolve` | unchanged (same code) | unchanged |

Interning 100,000 fresh `identifier_number_{i}` strings cost about 150 ns per
string on 1.0.1 and about 190 to 196 ns on 1.1.0 in two of the three runs; the
third run was too noisy to read. Growing the index rehashes every string, so
growth pays the extra hash cost again.

In short, about 6 to 9 ns more per intern or lookup. That buys a worst case
that cannot be prepared in advance.

## Compatibility

- No public item is removed or changed. `cargo semver-checks` against 1.0.1
  reports no breaking change.
- MSRV stays at 1.85.
- No new dependencies.
- Probe order, and so the order of slots in the index, now differs between
  interners. Nothing in the public API exposes it.
